# 架构推演：从"改写器"到"接地气的计划编译器"（v3 方向）

日期：2026/09/16　起因：坦克 3D 页面案例（一次优化生成 → 老板手动指挥 3 轮仍未达标）

## 一、角色与激励（用户给的最准确模型）

- **老板（用户）**：只给一个目标/指标，不接受需要多次指挥。
- **领导（优化 AI）**：必须把目标翻译成"员工一次就能执行到位"的封闭指令集。
- **员工（会话 AI，ds4.1f）**：能力很强，但**只做你明确说的**；不说的不碰、想不到的不查、不情愿多做。

## 二、为什么"再加几条规则"必然失败（三条底层原理）

**原理 1：信息不对称——没被"看到"的约束，绝不会进入提示词；没进入提示词的约束，必然被员工忽略。**
优化器是在**想象**中写计划，员工是在**真实**里执行。坦克案例里真正杀人的约束（WebGL1 下 `#extension` 必须在预处理之前、
FBO 在集显上不完整、色调映射曝光阈值、cubemap 自反馈 mipmap）**全都只能从真实环境里被发现**。
优化器从没见过这个仓库、没打开过这个页面 → 它的覆盖率有**架构上限**，不是提示词写得好不好的问题。

**原理 2：员工没有"注意到"的能力 ⇒ 提示词必须是封闭清单。**
任何"依赖员工自觉"的条目 = 没写。所以：**覆盖率 = 完成率**；验收项必须逐条可判定、逐条回执。

**原理 3：验证不能失败就毫无价值。**
本次实测：它的桩把 `COMPILE_STATUS` / `checkFramebufferStatus` 硬编码为成功——**把最容易出事的判定从验收里删掉了**。
验证器本身必须先被"已知坏样本"打脸（反控），否则只是装饰。

**推论（对应"蟑螂"问题）**：出错的不止这一只。**单点修补必然低效**——因为每一次修补只覆盖"这一只蟑螂"。
要根治，必须让"这一类问题"变成**可复用、可累积的数据**，对所有任务生效。

## 三、v3 架构：四层，数据与提示词分离

```
① 侦察层 Recon       ：先看再写——工作区事实包（目录树/清单/入口/已有产物/最近改动/交付媒介与打开方式）
② 计划层 Planner     ：事实包 + 用户目标 + 【领域清单库】 → 风险优先的封闭计划
③ 执行层 Worker      ：按清单逐项执行 + 逐项回执，不许增删（员工只需要"照单办事"）
④ 数据层 Checklists  ：按领域维护"完成必须为真"的条件集；每次失败回填；版本化
```

关键点：**提示词只是清单库的渲染器**。改进累积在**数据**里（清单条目、反控样本、失败案例），
不累积在提示词文字里——这才是从"修修补补"转向"体系增强"的分界线。

### 计划层必须产出的六件东西
1. **走路骨架优先（风险优先排序）**：先用最小代价证明"交付媒介里能跑起来"，再谈保真度。
   坦克案例中，顺序应当反过来：**先证明页面在真浏览器里能渲染出东西**，最后才做铆钉与细节。
2. **每步 = 动作 + 可观测预期 + 失败即停条件**（员工不会自己判断"算不算过"）。
3. **交付媒介自检**：页面内显示非黑像素比例 / FPS / 渲染器与资源加载状态 / onerror 捕获。
4. **反控**：验证器必须先用已知坏样本证明"它会报错"；桩不得替代关键判定。
5. **图像级断言**：非黑比例、过曝比例、剪影/纯色块占比、关键区域应出现的颜色与形状。
6. **覆盖审计**：清单库每一条是否都有"步骤 + 检查"；缺一即不得交付。

## 四、用坦克案例推演 v3（证明不是空话）

| 步 | v3 计划会怎么写 | 能拦住哪只蟑螂 |
| --- | --- | --- |
| 1 | 用真浏览器打开最小页面（只 `clearColor` 一个颜色），截图判"非黑且不纯色" | 媒介不可用 / WebGL 上下文创建失败 |
| 2 | 本地内联 three.js（**不依赖 CDN**），渲染一个立方体，页面自检回执 | 资源离线不可用、CDN 失败（本次黑屏第一嫌疑） |
| 3 | 接入真实场景，判过曝比例与剪影占比上限 | 本次第三轮的"半个天球被泛光灌爆 → 全白 + 洋红" |
| 4 | 逐段分离：几何 → 光照材质 → 后处理合成 → 色调映射，用中间输出对比 | FBO 不完整、cubemap mipmap、着色器变体失败 |
| 5 | 材质与细节（铆钉、工具箱、探照灯…） | 保真度问题（**放在最后，失败也不致命**） |
| 6 | 反控：故意喂一个必坏的着色器，确认自检会红 | "桩硬编码成功"这类验证漏洞 |

结论：**原始案例中"做完 304 颗铆钉才发现屏幕全黑"的顺序，是架构缺陷的必然结果**——因为它没有"风险优先"这一层，
也没有任何机制强迫它在真实媒介里先跑一次。

## 五、落地分期

- **P0 清单库**：定义数据结构（领域 → 条件条目 → 检查方式 → 反控样本），先写 3 个领域：
  `web-3D 交付`、`单文件 HTML 工具`、`CLI/脚本`。渲染器把清单注入系统提示词。
- **P1 侦察**：把工作区事实喂给优化器（目录树 / 清单文件 / 入口 / 已有产物 / 是否存在截图）。
  需要决策：优化器是"带只读工具的侦察 pass"，还是"由插件注入上下文"（后者快、前者准）。
- **P2 计划规范**：风险优先 + 六件产出 + 覆盖审计自检（机械可判：清单条目 ↔ 步骤/检查 的映射完整性）。
- **P3 测试台门**：真实媒介验收（无头浏览器 + canvas 像素统计）+ 图像级断言 + 反控题类。全零 LLM 参与。
- **P4 回填闭环**：每次交付暴露的新失败模式 → 写回清单库（版本化）→ 用旧失败案例做回归。

## 六、明确不做
- 不再往提示词里逐条加规则（v2.x 的做法到此为止，保留为可对照版本）。
- 不做"区域专项化的东补一块西补一块"：领域差异一律进**清单库**，不进代码分支。
