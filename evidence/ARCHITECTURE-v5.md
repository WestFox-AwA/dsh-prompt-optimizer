# 架构 v5：只补全要求（Requirement Completion Only）

日期：2026/09/16　状态：**已上线**（`STRATEGY = 'v5'`，热重载生效）

## 一、这次是"减法"，推翻了 v2/v4/v4.1 的共同假设

v2（作业指导书）、v4（探针优先）、v4.1（覆盖优先 + 终局验证）虽然在取舍上不同，但都默认了同一件事：
**优化器应当管理员工的工作方式**——给它步骤、给它验收清单、给它验证纪律、给它禁止事项。

这个假设是错的。三条底层推理：

1. **优化器的唯一价值是补上用户没说的内容。** 除此之外写的每一个字，都是在替员工做它本来就会做的事。
2. **复述通用能力＝教它已经会的东西。** v4.1f 具备基本的验收与认知能力（它会看、会比对、会跑一下）。
   把这些写进去只占它的注意力预算——实测表现就是输出膨胀：旧策略要求"逐步验证并贴证据"，
   把执行端程序撑爆，**10/24 格被判预算截断而白扔**。
3. **禁止性措辞有副作用**：它把注意力引到被禁止的事情上，并收窄解法空间
   （"不许用临时手段掩盖问题"会让它不敢碰渲染设置——这与用户"权限太少、限制太多"的观察一致）。

## 二、正确分工

```
用户（老板）  ：只给意图（短、模糊）
优化器（领导）：只补全"要什么"——内容层
员工（v4.1f） ：怎么做、怎么验——能力层（本来就有）
```

**"验收"不再作为检查清单存在，而是写成"使用情形与结果的样子"。**
例：不写"验收：履带可见"，而写"用户双击这个文件就能看到坦克，不需要装任何东西、也不需要联网"。
它是内容；员工自己会去满足并确认。

## 三、v5 的实现（系统提示词 515 字符）

只做一件事：把用户的一句话补全成一份完整具体的要求说明。补全维度（内容，不是清单）：
对象消解 → 结果是什么样子 → 用户会怎么用它 → 感觉类的话说具体 → 边界情形 → 范围。
写法要求仅一句："用陈述句写是什么、要什么，像一份写得极好的需求说明。"
歧义按最保守理解并注明「按 X 理解」。

**明确删除**：流程编排、步骤安排、验收清单、验证纪律、探针、回执格式、禁止事项、通用教学。

v5 的实际产出（节选，未经编辑）：
> 请修复当前项目中坦克的履带显示不出来的问题。这里的"坦克"按项目里已有的那个坦克模型/图形理解。现象是：坦克主体能正常显示，但履带部分不可见……
> 在常见使用情形下都要成立：正常加载页面或启动程序后，坦克一出现履带就可见；改变窗口大小、缩放比例、切换主题或语言时，履带不消失、不闪烁、不错位。
> 边界处理：如果原因是资源缺失或路径错误，请恢复正确的资源引用；如果原因是代码或渲染逻辑导致履带被隐藏，请修正逻辑让履带显示出来；加载异常时按项目现有错误处理方式处理，不要静默隐藏。
> 范围限定：只修复坦克履带的显示问题……修复完成后，打开项目找到坦克，应能看到完整坦克（包括履带），且无相关报错。

注意最后一句：**它是"打开就能看到"这样的内容陈述，而不是"你必须验证"这样的管理指令**——覆盖度由内容承担，检查由员工自己做。
