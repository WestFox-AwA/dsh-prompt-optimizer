# 案例：坦克 3D 页面交付后画面全黑（2026/09/16）

## 现象
- 用户双击打开交付的 HTML：**UI 面板正常显示，3D 画面全黑**。
- 交付方（v4.1f，PTC 模式）交出了极其详实的自证：stub 掉 GL/DOM 用 Node 跑通引擎启动流程（63760 三角形、履带 76 块/侧、
  轮系切点误差 0.0000、304 颗铆钉、差速/炮塔限位数值……），并**自写软件光栅化器**渲了 6 张 PNG，逐张看过，还揪出 4 个真 bug。
- 它同时声明："浏览器自动化在这台机器上不稳定（Edge 提权 + 沙箱下 CDP 连接反复被拒）"，
  并在结尾写"**我没能验证的（需要你的眼睛）**：3D 实际画面、HUD 排版、1080p 极致档 FPS"。

## 判定器（我，据两张截图给出的高置信度推断）
第二张图（真实页面）里 HUD 显示：`帧率 — FPS`、`帧时 / 三角形 — / —`、`画质档 / 分辨率 极致 / —`——
**三个数值全是占位符**，说明渲染循环**从未把数据回报**，即 3D 初始化在首帧之前就失败了；而纯 DOM 的 UI 面板正常，
说明页面 JS 本身在跑。故最可能的根因（按概率排序）：
1. three.js 从 CDN 加载失败（离线 / 被拦 / 版本 URL 失效）→ 场景根本没建起来；
2. WebGL 上下文创建失败（显卡/权限/无头环境）→ renderer 未创建；
3. 初始化期抛异常（着色器编译、材质、几何参数 NaN）→ 循环未启动。

## 根因不在能力，在**验证层级**
交付方验的全是**代理**：stub 引擎 + 离线光栅化。这两条路径**都绕过了真实渲染管线**，
所以"UI 正常、画面全黑"这类**初始化失败**在它们那里永远看不见。这正是"验证做了很多、真错一处没查到"的又一层形态。

## 由此新增的策略规则（v2.2，已上线）
1. **验收必须在交付媒介里做**；代理手段（stub、自写渲染器、单测）**只能用来定位，不能用来宣告完成**。
2. 真实媒介用不了时：**先换手段继续试**（换浏览器 / 换 user-data-dir / 无头 / --no-sandbox / 换端口），
   并在交付说明里写下试过的命令与报错原文；穷尽后才能上报"未在真实媒介验证"，且对应验收项**必须标未通过**。
3. **交付物自带可观测自检**：页面内显示非黑像素比例 / FPS / 渲染器与资源加载状态 / onerror 与 WebGL 上下文丢失捕获。
4. **外部资源不得依赖不可达来源**：CDN/字体/模型要么本地化内联，要么显式声明并给离线替代——否则用户双击就是黑屏。
5. **手段全开，范围冻结**：手段不设限（起浏览器、截图、录屏、跑构建、临时诊断代码），范围划死（只做要的那件事）。
6. **交付就绪门**：双击/一条命令能看到结果；在真实媒介里亲眼看到预期现象；没有"永远为真"的检查；未过项如实标未通过。

## 后续（交付方又迭代两轮，2026/09/16 同日）

### 第二轮：它自己找到了"验证为什么没抓到"
原话要点：**它的 Node 验证桩把 `getShaderParameter(COMPILE_STATUS)` 与 `checkFramebufferStatus()` 硬编码成"永远成功"**
（return true / complete），等于把「着色器能不能编译」「帧缓冲能不能用」这两个最容易出事的判定**从验收里删掉了**；黑屏恰恰藏在被跳过的那两块。

它随后修掉三个能导致全黑的真 bug：① `makeFBO` 从不调 `checkFramebufferStatus` → 帧缓冲不完整、几何画进空气里（改成逐级降级重试 + 全失败则直渲屏幕）；
② WebGL1 路径缺 `#extension GL_EXT_shader_texture_lod : enable`，且指令必须在所有非预处理语句之前（原来 precision 在前）→ PBR/INST 着色器编译失败 → 每帧清屏后中断；
③ 辐照度立方体贴图在自己还挂在 FBO 上时 `generateMipmap` → `INVALID_OPERATION`，mipmap 未生成而 `minFilter` 要 mipmap → 纹理不完整 → 环境漫反射全黑。
顺带修：`state.ssao` 拼错致 SSAO 永关、`setLighting` 空指针、法线贴图 `UNPACK_ALIGNMENT`。

### 第三轮：真正的 bug 是 GLSL ES 3.00 不接受 int→float 隐式转换
instanced 片元着色器第 109 行 `.../(NODotV*(1-k)+k)` 里写的是 `1` 而不是 `1.0` → `const int - highp float` 编译失败（PBR 那一份写的是 `1.0-k`，只有 instanced 漏了小数点）。

### 第四轮：能渲染了（165 FPS / 109k 三角形 / 1147×1288），但**视觉效果完全不对**
用户截图显示：大面积过曝成纯白、黑色剪影、粉色亮线。即问题已不在编译，而在**光照/材质/后处理/色调映射这一段输出**——
"没报错、有帧率"照样过不了验收。

## 三层教训（已写进策略 v2.2 / v2.3）
| 层 | 失败形态 | 新规则 |
| --- | --- | --- |
| 1 | 用代理手段（stub 引擎 / 自写光栅化）宣告完成 | 验收必须在**交付媒介**里做；代理只能定位 |
| 2 | 桩把关键判定硬编码为"永远成功" | **验证器必须先被验证（反控）**：拿已知坏样本跑一遍，确认它真的会报错；关键判定不得跳过或返回恒定值 |
| 3 | 能渲染但效果错，"没报错"被当通过 | **图像级断言**：非黑像素比例、亮度/曝光分布、关键区域颜色形状、与参考图差异；判断"效果不对"按**管线阶段**逐段分离定位 |

## 待办（把这类失败变成可机械判定的题）

- 新题类：**"交付必须经得起真实媒介验收"**——判定器用无头浏览器打开产物，计算 canvas 的**非黑像素比例**
  与页面自检回执（renderer 是否创建、onerror 是否为空），而不是只看 HTML 文本。已知风险：本机 Edge 无头截图在早前实测不稳定，
  需先用 CDP 路径验证（测试台曾有一格通过 CDP 成功取到自检输出）。
- 进阶题类（对应第三层教训）：**图像级断言**——除了"非黑"，还要判**过曝比例**（接近纯白的像素占比上限）、
  **剪影/纯色块占比**、以及"关键区域应出现的颜色"；判定器直接对截图做像素统计，机械可判、无 LLM 参与。
- 反控题类（对应第二层教训）：给一份**已知会在真环境失败**的产物（例如桩里必定成功、真跑必报错的着色器），
  看解答者的自检是否能报出来——即"**验证器的反控**"。
