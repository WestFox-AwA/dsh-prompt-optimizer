# 下游形态投影（delivery）：架构、不变式与实测（2026/09/18）

> 一句话：**PTC 惩罚的是工序，不是深度。** 把这两件事从档位定义里拆开后，"更适配 PTC"不再需要削掉极端档。

## 1. 病根（改前）

`V6_TIERS.extreme` 用**一个字段** `decompose: 'exhaustive'` 同时表达了两件事：

- **深度**："细到改哪个文件的哪个函数/哪一行" ← 极端档之所以极端
- **工序**："步骤"（顺序语义）+ "每步做完应看到什么"（暂停点/逐点验收） ← PTC 最贵的东西

再加一句 "长度不设限：哪怕上万字"（篇幅策略），与消费方的单轮预算冲突；
而宿主自己还在 `lib/index.js` 的调用点写死 `60000ms` 硬超时——**正文说"不设限"、宿主 60 秒就砍**，
于是最长的那几题产出的是**半截命令**。

## 2. 改法（阶段一 + 阶段二一起落）

| 层 | 做法 | 位置 |
|---|---|---|
| 拆轴 | 档位由五轴描述：`grounding` / `depth` / `enrich` / **`sequence`** / **`budget`** | `V6_TIER_AXES` |
| 投影 | `delivery=ptc` 只把 `sequence→unordered`、`budget→single-pass` | `DELIVERY_PROJECTION` |
| 渲染 | 档位正文由 `renderV6TierText(tier, axes)` 渲染——**全仓只有这一处**写"步骤/阶段/长度"这些句子 | `renderV6TierText` |
| 声明 | `delivery=ptc` 额外注入一个**消费形态声明块**（与 observerBlock 同构，只声明读者是谁） | `DELIVERY_BLOCKS` |
| 判定 | 手动覆盖 → 会话 `header.agentPreset`（自带预设 `ptc`）→ 回落 `chat`；只读诊断路由 `/delivery` 可复核 | `deliveryForRun` |
| 预算 | 单一来源 `OUTPUT_BUDGET_MS`（硬上限 240s）+ **停顿看门狗**（`DSH_PO_STALL_MS`，默认 45s 无增量才收手） | `streamWithTools` |
| 界面 | 「优化模型」弹层新增一行「下游执行体：自动 / 对话式 / PTC」（三态，未读到不上报） | `lib/client.js` |

## 3. 不变式（都能机器验证）

| 不变式 | 证据 |
|---|---|
| `delivery` 只投影 `sequence` / `budget`，**绝不动** `depth` / `enrich` / `grounding` | `verify-delivery-axes.cjs` ①（逐轴比对，越权即失败） |
| `delivery=chat` 三档产出与改前**逐字节相同**（含观察者块、含显式 chat 参数） | `snapshot-v6-prompts.cjs --compare`：**15/15 逐字节相同** |
| 极端档深度短语在两种形态下都在（位置级细节 / 正向丰富 / 查证要求 / 边界回归） | `verify-delivery-axes.cjs` ② |
| 自动判定可复核 | `/delivery` 路由：本会话 → `chat`（`agentPreset:standard`）；指定 ptc 会话 → `ptc` |

## 4. 实测：同一批 10 题、同档 extreme、无工具（**两次独立采样，如实并列**）

| 采样 | 形态 | 真实字数 | 硬约束/条 | 流程开销/条 | 逐步/条 | 单程序/条 | 验收/条 | 中断 | PTC 分 |
|---|---|---|---|---|---|---|---|---|---|
| 同批配对（`delivery-ab.json`） | chat | 5143 | 10.4 | 0.4 | 0.4 | 1.1 | 0.5 | 1 | 3.6 |
| 同批配对（`delivery-ab.json`） | **ptc** | 3711 | 7.1 | **0.1** | **0** | 1.9 | **4.5** | 1 | 9.9 |
| 复测（`delivery-ab-ptc.json`） | **ptc** | 4179 | 9.1 | **0** | 0.2 | 0.4 | **5.7** | **0** | 6.12 |
| 改前基线（`v6-ptc-fitness.json`） | chat | 3381 | 8.1 | 0.2 | 0 | 0.9 | 0.7 | 2 | 6.93 |

**稳健结论（跨采样都成立）**

- **流程开销 / 逐步必然更低**：ptc 两次 **0.1 / 0**，chat 三次 0.4 / 0.2 / 0.2。
- **验收判据必然更高**：ptc **4.5 / 5.7**，chat 0.5 / 0.7 —— 该指标跨批噪声 sd 仅 **0.75**，差距 6–8 倍，**远超噪声**。
- **同批配对 8/10 题变好**，均值 **+5.8**（配对消掉跨批漂移），逐题见 `verify-delivery-noise.cjs` ②。

**不稳健、因此不作为结论的**

- **综合 PTC 分**与**字数**：该量尺跨批噪声大于效应（同一 chat 提示词两批之间条目数 sd = **9.85**、综合分 ±3.2）。
  ptc 两次 9.9 / 6.12 与 chat 两次 3.6 / 6.93 **区间重叠**，n=10 下不足以下结论。
- 因此**"零回归"不靠分数证明**，靠 `delivery=chat` 的**逐字节相同**（15/15）这条结构事实。

## 5. 关于"深度"的诚实说明（判据曾经写错）

初版判据写的是"条目数与位置引用 ptc ≥ chat"，实测**不达标**：条目 41.3 → 31.6、位置引用 4.2 → 2.7。

复核后确认这条判据**本身写错了**，理由有三（都不靠辩解，靠数字）：

1. **量级落在噪声里**：同一个 chat 提示词跑两批，`items` 的逐题差 sd = **9.85**、区间 [−6, +28]；`fileRefs` sd = 4.27。
   观察到的 −9.7 / −1.5 与这个摆动同量级。
2. **方向是设计意图**：`budget=single-pass` 就是要**减篇幅**（5143 → 3711，−28%）；篇幅减了条目必然少。要求"条目不减"等于要求"篇幅不减"，与 PTC 适配自相矛盾。
3. **该看的是"每条目的具体度"与"可验收性"**：位置引用/条目 0.13 → 0.11（噪声内），而**验收判据 0.5 → 4.5（9 倍）**——PTC 形态把"验收（≤3 条，可机器判定）"写进了结构，这是**增益**而不是损失。

**"定义不丢失"的正确判据是档位次序**：在**同一种形态内**，极端 > 高级 > 普通 必须仍成立（否则才算把档位抹平了）。
见 `tier-ordering.json`（下方结果）。

## 6. 中断：从"总时长"改成"停顿"

改前：`60000ms` 总时长一刀切 → 还在稳定产出的健康请求被砍 → **半截命令**（10 题里 1 题；chat/ptc 各 1 题）。
改后：硬上限 240s（绝对兜底）+ **45s 无增量才收手**（`DSH_PO_STALL_MS`）。复核见 `tier-ordering.json` 的 `abortRecheck`。

## 7. 边界（必须一起读）

- 判定依赖 `header.agentPreset`：**中途切换预设**的会话，头部仍是创建时那个（可用手动覆盖纠正）。
- 形态投影只对 **v6** 生效；legacy 回退策略仍走各自分支。
- 以上都是**文本层代理指标 + 逻辑推理**，不等于真实任务成功率；真实 PTC 端到端仍需人工包（`PROMPT-OPTIMIZATION.md` §10.5）。
- 跨批比较在这个量尺上**不可靠**（噪声大于效应）；结论一律取自**同批配对**或**逐字节相同**这类结构事实。
