# v6 是否适合 PTC：逻辑推理 + 同尺实测（2026/09/18）

> 结论先说：**v6 的契约层是 PTC 友好的，比 0.1.1+PTC_RULES 的补丁式三条更结构化；但"极端档"有三处与 PTC 消费方式实打实冲突**。
> README 顶部"针对 PTC 模式优化"的方向成立，但"建议在 PTC 模式下使用"需要加限定。

## 1. PTC 的消费方式（项目已查清的环境事实，非我的推测）

- `PROMPT-OPTIMIZATION.md:373`：DSH 自带预设 `ptc`：功能完整的编码 Agent，**默认不提供 workflow 工具**；其他工具通过 PTC SDK 呈现，**让模型用一个 TypeScript 程序组合多步操作**。
- `:374`：因此 PTC 的消费方式是"**一个程序、一次执行**"，每次往返都要重新起程序 —— 与"逐步/逐层/每阶段贴输出"这类节奏**天然冲突**。
- `evidence/ptc-ab.cjs:5`（项目自己的量尺口径）：好命令应当是"要求少而硬、利于一次成程序、留出实现自由、不堆流程开销、别把用户可见交互降级"。
- `evidence/ptc-lab/README.md:190`（实测教训）：过度约束会"**把执行端程序撑过单轮输出上限 → 浪费轮次**"。

由此得到三条判据：**① 不强制多轮往返；② 不堆流程开销/清单；③ 篇幅不能顶爆单轮预算。**

## 2. 逐条对照 v6 的定义（逻辑推理，全部有行号依据）

### 2.1 契约层 `V6_CORE`（`lib/index.js:647-651`）——**PTC 友好**

| 条款 | 与 PTC 的关系 | 判 |
|---|---|---|
| 【产出即命令】不解释/不提问/不自述过程，也**不要写流程仪式（阶段闸门/打勾/贴证据/失败预案清单）或通用教学** | 这正是 0.3.x 被判"PTC 敌对"的两类：**闸门类**强制多轮（PTC 里最贵）、**清单类**挤占程序上下文 | ✅ 友好 |
| 【保真】不新增功能，但补齐"做对必须满足的条件"（边界/错误路径/不许碰/兼容性） | 这是**结果约束**，不是**节奏约束**；PTC 忌的是多轮往返，不是"结果要满足什么" | ✅ 友好（密度需控制） |
| 【语言层】【歧义】 | 与消费方式无关 | ⚪ 中性 |

**关键判断**：v6 用"收件人契约"（产出物只对工作 AI 说话）**从机制上**推出了"禁止流程仪式"，这与 `PTC_RULES` 的 A 条（不得要求分阶段/逐步/每阶段贴输出/先建 goal·todo）与 C 条（不写失败预案）**目标一致，但更结构化**——不是补丁式的注意事项，而是"产出物收件人"这一层架构的推论。

### 2.2 档位层 `V6_TIERS`（`lib/index.js:653-687`）——**分歧就在这里**

| 档位 | 定义要点 | 与 PTC | 判 |
|---|---|---|---|
| 普通 basic | 只依据原话与已给上下文；**不派工具**；长度跟随原话（可压缩） | 短、零流程开销、无多轮诱导 | ✅ **最佳** |
| 高级 advanced | 输出结构：目标 → 现状事实 → **阶段性任务（阶段 1/2/3：每阶段做什么、做到什么程度、怎么算做完）** → 边界 | "阶段性任务"与"一个程序一次做完"存在张力：下游若按字面读成"每阶段一轮"，正是 PTC 最贵的形状 | ⚠️ **有风险** |
| 极端 extreme | **步骤**（细到改哪个文件的哪个函数/哪一行，**每步写清做完后应看到什么**）+ 【正向丰富】+ **长度不设限：哪怕上万字** | (a) "每步做完应看到什么"≈逐阶段验收；(b) 上万字**直接顶单轮输出预算** | ⚠️⚠️ **最冲突** |

**必须说清的一个区别**：v6 的"阶段/步骤"是**任务内容的分块**（交付什么），不是"停下来汇报"的节奏；但 v6 的**语言层没有禁止"分阶段/逐步"这类措辞**，而下游是**按字面读**的。这是 v6 相对 `0.1.1 + PTC_RULES` 唯一的实质性缺口——`PTC_RULES` 的 A 条正是为此而写。

## 3. 同尺实测（同一把尺、同一批题、同档 extreme、无工具）

数据：`evidence/v6-ptc-fitness.json`；脚本 `evidence/verify-v6-ptc.cjs`（量尺与公式**逐字取自** `ptc-ab.cjs:35-49` 与 `:74`，未改公式）；题目 `evidence/lab-cx.json` 全 10 题。
对照值取自 `evidence/ptc-fitness.json`（0.1.1 与 0.3.8 各 20 格）。

| 条件 | 格 | 平均字数 | 硬约束/条 | 流程开销/条 | 逐步/条 | 自由度/条 | 单程序/条 | 交互/条 | 验收/条 | **PTC 分** |
|---|---|---|---|---|---|---|---|---|---|---|
| **v6（本版活实例）** | 10 | 3381* | 8.1 | **0.2** | **0** | 0.3 | 0.9 | 6.7 | 0.7 | **+6.93** |
| V011-extreme（0.1.1） | 20 | 1822 | 3.2 | 2.85 | 0.5 | 0.2 | 0 | 4.7 | 1.7 | +1.93 |
| V038-extreme（0.3.8） | 20 | 2699 | 30.55 | 9.9 | 0.5 | 0.1 | 0 | 11.7 | 5.3 | −17.52 |

\* 3381 是**被截断到 4000 字符**后的统计口径；**真实平均长度 5029 字**（逐题：6462 / 10459 / 8314 / 1955 / 3257 / 3200 / 3136 / 2261 / 5139 / 6110）。

**三点发现：**

1. **PTC 分 +6.93，高于 0.1.1（+1.93），远高于被判 PTC 敌对的 0.3.8（−17.52）。** 决定性差异项是**流程开销 0.2/条**（0.1.1 2.85、0.3.8 9.9）与**逐步 0/条**——这两项正是 0.3.x 回退的依据，而 v6 把它们压到了下限。
2. **口径警告（不可忽略）**：`/runs` 的 `text` 截断在 4000 字符，10 题里 6 题触顶，而历史值是**全文**。截断把**所有**密度类计数一起少算（正项与负项同时被低估，方向不确定）；按平均捕获率 ≈0.79 反推，分数落在 **+6 ~ +8** 区间——**不影响结论**，因为流程开销 0.2×1.27≈0.25 仍比 0.1.1 的 2.85 低一个量级。
3. ⚠️⚠️ **新发现的硬失败模式**：v6 极端档真实产出**平均约 5029 字**（0.1.1 的 2.8 倍、0.3.8 的 1.9 倍），其中 **2/10 题直接撞上 60 秒硬超时**（`lib/index.js:2077` / `:2083` 把预算写死为 `60000`，`streamWithTools:1418` 用它做 abort）→ `llm-aborted`，**只写出半截命令**（在第 6462 / 10459 字处被砍）。
   对 PTC 尤其致命：下游拿到的是**没有收尾边界/验收**的命令，而"一个程序一次做完"最怕半截规格 —— 这正是判据 ③ 被打破的样子。

## 4. 结论

1. **v6 整体适合 PTC**：契约层（收件人 + 产出即命令）从机制上禁止了 PTC 最贵的两类要求，实测流程开销 0.2/条、逐步 0/条，PTC 分在三者中最高。
2. **不适合 PTC 的是极端档的三点**，且**不是措辞问题而是行为问题**：
   - 长度：平均 5029 字，顶单轮输出预算；
   - 超时：2/10 题 60 秒被中断，产出半截（这是**当前的真实缺陷**，与 PTC 无关也该修）；
   - 结构：高级/极端档明文要求"阶段性任务/步骤"，而语言层没有 `PTC_RULES` A 条那句禁令。
3. **对 README 横幅的建议**：方向**成立**（v6 的契约层就是为"命令型消费者"设计的），但"建议在 PTC 模式下使用"应当补一句限定：**PTC 下推荐普通/高级；用极端档要接受长产出与 60 秒中断风险**。
4. **若要彻底对齐 PTC（需你点头，因为这会改三档定义）**，最小改动是两处：
   - 在 `V6_CORE` 的【产出即命令】补一句"**不得要求分阶段/逐步/每阶段贴输出/先建 goal·todo**"（等价于 `PTC_RULES` 的 A 条）；
   - 把极端档的"长度不设限：哪怕上万字"改为"**够用即止，但不得省掉必要边界**"。
   我**没有动**这两处——它直接改三档定义。

## 5. 诚实边界（必须一起读）

- 这是**文本层代理指标 + 逻辑推理**，**不等于**真实任务成功率；项目此前也反复声明"未在真 PTC 环境端到端验证"（`PROMPT-OPTIMIZATION.md:405-408`）。
- v6 的 n=10（1 次/题），历史值 n=20（2 次/题）；`/runs` 截断见上。
- 本次测量**关闭了只读工具**（对齐历史条件）；默认开启时产出还会多出"查证事实"的部分，长度只会更长。
- 60 秒超时是**代码事实**（`:2077`/`:2083`），2/10 的命中率是**这一次 10 题样本**的观测值。
